Build the system design from the findings below: enough to draw an accurate diagram of the system as it is today and as the target describes it. Submit the whole design every time: a row of the current design you leave out is removed. Keep a row by giving its ID as its key, [[C03]]; give a new row a new key, [[c1]]. Write every reference in double brackets, [[F07]] or [[c1]]. Each row rests on findings, or on what explains it: a gap, an open decision or a scope decision.

1. Boundaries: what groups components. within is the boundary it sits in, such as a cluster within a cloud account, or None. kind starts with one of: {{boundary_kinds}}, then any detail, such as "cloud account: eu-west-2".
2. Components: every part that runs, stores or talks across a boundary, such as a service, job, library that calls out, store, queue or external product, and the people or roles that act on it. kind starts with one of: {{component_types}}, then any detail. boundary is the boundary it sits in, or None. Challenge a generic noun, such as "platform" or "gateway": what runs where, called by whom, and what proves it exists. code links its repository and paths at the pinned revision, or says None. state starts with one of: {{statuses}}. A component is in the state its strongest evidence shows. {{precedence}} An external product, a person or a role is 🟩 once a finding shows it exists, whether or not {{topic}} uses it yet: its connections' state says that. Any other 🟩 or 🟦 needs a code source with coverage {{read_coverage}} of a path it links, a file under it or a folder above it; 🟨 needs a finding read in the tracker among its evidence, 🟪 one read in the documentation.
3. Identities: the credentials or accounts connections use, and what each can reach, citing the components, such as "Retrieve on [[C03]]"; several connections often share one. kind starts with one of: {{identity_kinds}}, then any detail, such as "cloud role: AWS IAM, assumed by a managed service". The script gives each identity the most advanced state of the connections that use it.
4. Connections: who calls whom (from and to, one component each), how, starting with one of: {{connection_kinds}}, then any detail, such as "HTTP: POST /search", with what data, whether the caller waits for a reply (waits_for_reply starts with one of: {{waits}}), with which identity (or None, or Unknown), and its state, as for components.
5. Flows: for each entry point that matters, the connections it uses, in the order they happen: each after the first starts from a component the flow has already reached. The script gives each flow the state of its least advanced verified connection, naming any unverified step, such as "🟩 Live, unverified: E01", so the entry point doesn't say it.
6. Unknowns: a component or connection you can't establish is ⬜ Unverified, with the gap that explains it in evidence; a row the target leaves waiting on an open choice cites the decision, [[D01]], beside its findings; a caller you can't identify is a component of kind unknown. Never guess one.

A component, a connection, an identity and a flow each say in in_the_target how the target changes them, citing the evidence, such as "Replaced by the sync job ([[F12]])" or "Removed once sync runs ([[F14]])", or Unchanged. A row only the target has says what it adds, citing its evidence.

Draw no other part of it, except one {{topic}}'s own code calls or uses itself, such as a store its service connects to or the service its manifests are applied by, as a component of its own; draw nothing behind such a part, and nothing {{topic}} reaches only through another part. Each part you draw is in the state the evidence on the side of {{topic}} shows, as for an external product; where that evidence doesn't establish it, it is ⬜ Unverified, with the scope decision that explains it in evidence, such as [[U02]], since the user chose not to research it. Draw nothing the user excluded, even where a finding names a connection to it.
