Build the system design from the findings below: enough to draw an accurate diagram of the system as it is today and as the target describes it. Submit the whole design every time: a row of the current design you leave out is removed. Keep a row by giving its ID as its key, [[C03]]; give a new row a new key, [[c1]]. Write every reference in double brackets, [[F07]] or [[c1]]. Each row rests on findings, or on what explains it: a gap, an open decision or a scope decision.

1. Components: every part that runs, stores or talks across a boundary, such as a service, job, library that calls out, store, queue or external product, and the people or roles that act on it. name_and_type is the name, then its type in brackets, one of: {{component_types}}, such as "Search API (service)". Challenge a generic noun, such as "platform" or "gateway": what runs where, called by whom, and what proves it exists. code links its repository and paths at the pinned revision, or says None. status starts with one of: {{statuses}}. A component is in the state its strongest evidence shows. {{precedence}} 🟩 and 🟦 need a code source with coverage {{read_coverage}} of a path it links, a file under it or a folder above it; 🟨 needs a finding read in the tracker among its evidence, 🟪 one read in the documentation. in_the_target says how the target changes it, citing the evidence, such as "Replaced by the sync job ([[F12]])", or Unchanged. boundary is the boundary it sits in, or None.
2. Connections: who calls whom (from and to, one component each), how, starting with one of: {{connection_kinds}}, then any detail, such as "HTTP: POST /search", with what data, whether the caller waits for a reply (waits_for_reply starts with {{waits}}), with which identity (or None, or Unknown), and its state, as for components.
3. Boundaries: what groups components. kind starts with one of: {{boundary_kinds}}, then any detail, such as "cloud account: eu-west-2".
4. Identities: the credentials or accounts connections use, and what each can reach; several connections often share one. kind starts with one of: {{identity_kinds}}, then any detail, such as "cloud role: AWS IAM, assumed by Bedrock". The script gives each identity the most advanced state of the connections that use it.
5. Flows: for each entry point that matters, the connections it uses, in the order they happen: each after the first starts from a component the flow has already reached. The script gives each flow the state of its least advanced connection, so the entry point doesn't say it.
6. Unknowns: a component or connection you can't establish is ⬜ Unverified, with the gap that explains it in evidence; a row the target leaves waiting on an open choice cites the decision, [[D01]], beside its findings; a caller you can't identify is a component of unknown type. Never guess one.

A topic the user decided as mention only is a black box: draw it only where evidence on the side of {{topic}} connects it to {{topic}}, as one component or as the boundary {{topic}} runs in, whichever that evidence shows, drawing none of its own parts. As a component it is ⬜ Unverified, with the scope decision that explains it in evidence, such as [[U02]]. Draw nothing the user excluded, even where a finding names a connection to it.

The findings name their sources, and each source's coverage names exactly what was read. When a finding is there but too thin to fill a row, re-open its source at that place first: that makes known evidence precise, it adds nothing new.
